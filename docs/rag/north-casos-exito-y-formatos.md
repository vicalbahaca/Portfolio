# North: casos de éxito, copys y formatos de presentación

## Estado y procedencia

Referencia extraída de 15 slides compartidas por Victor el 23 de julio de 2026. El material combina:

- Una guía corporativa para construir casos de éxito.
- Plantillas para presentar mobile, web, Design Systems, research y vídeo.
- Casos de CaixaBank Payments & Consumer y Facilitea.

Las slides son una **fuente interna de empresa**. Sirven para estructurar y redactar el portfolio, pero sus cifras, logos, pantallas y afirmaciones no se consideran automáticamente aprobados para publicación externa.

Estado de evidencia utilizado en este documento:

- `regla-corporativa`: criterio editorial o visual definido en la guía de North.
- `fuente-empresa`: hecho o cifra presente en una slide proporcionada por Victor.
- `pendiente-aprobacion`: requiere validar uso externo, fuente original o aprobación de Growth.
- `verificada-publica`: contrastada además con una fuente pública.

## 1. Principio superior

Todos los casos deben compartir estructura, tono, nivel de detalle y criterios de seguridad. La forma visual puede cambiar según el proyecto, pero el lector siempre debe poder responder:

1. Qué problema o transformación aborda el caso.
2. Qué responsabilidad tuvo Victor.
3. Cómo se trabajó y qué decisiones se tomaron.
4. Qué se entregó.
5. Qué cambió y con qué evidencia.
6. Qué información se ha anonimizado o limitado.

## 2. Estructura corporativa trasladable

La guía de North propone nueve elementos:

1. **Logo del cliente**: visible, en blanco cuando el fondo lo requiera y sin competir con el contenido.
2. **Título descriptivo**: debe expresar el objetivo o la transformación; la marca se incluye solo cuando aporta contexto y es seguro nombrarla.
3. **Tags de servicio**: únicamente los relevantes para el caso.
4. **Texto introductorio**: reto y contexto inicial explicados brevemente.
5. **Nuestra colaboración**: qué se hizo, cómo se abordó y qué valor aportó.
6. **Resultados**: cualitativos o cuantitativos, siempre reales y relevantes.
7. **Mockups y visuales**: pantallas completas, planas y centradas en decisiones UX.
8. **Estilo y tono**: lenguaje conciso, directo, profesional y creíble.
9. **Aprobación final**: validación del equipo de Growth antes de compartir material corporativo externamente.

### Adaptación al portfolio personal

La slide corporativa prescribe primera persona del plural. En el portfolio de Victor se aplica esta regla:

- Usar **primera persona singular** para responsabilidad individual: `definí`, `estructuré`, `diseñé`, `coordiné`, `validé`.
- Usar **primera persona plural** para trabajo realmente colectivo: `con el equipo diseñamos`, `acordamos con tecnología`, `validamos con negocio`.
- No convertir un resultado del equipo en una atribución individual.
- No usar una voz impersonal basada en infinitivos cuando oculte quién tomó la decisión.

## 3. Tags de servicio

Vocabulario corporativo disponible:

- UX/UI
- Design System
- Implantación
- Desarrollo
- Research
- Motion
- Accesibilidad
- CRO
- Dirección de arte
- Brand
- Content
- DesignOps
- SEO
- Ecommerce

Reglas de uso:

- Seleccionar entre dos y cuatro tags que expliquen realmente el alcance.
- No usar tags como keywords decorativas.
- `Implantación` requiere participación demostrable en delivery o adopción.
- `Desarrollo` solo cuando el caso incluya trabajo de ingeniería.
- `CRO` requiere una hipótesis, intervención o métrica vinculada a conversión.

## 4. Biblioteca de formatos visuales

### Regla base para mockups

- Priorizar pantallas completas y legibles.
- Usar composiciones planas, sin marcos de dispositivos cuando no añadan información.
- Mostrar elementos UX que demuestren una decisión.
- Evitar cortes arbitrarios y composiciones meramente estéticas.
- No mostrar datos personales, identificadores, URLs internas ni reglas sensibles.

### Mobile

Usar cuando el valor esté en:

- Navegación, botones y jerarquía en pantalla pequeña.
- Compra, contratación o personalización.
- Una funcionalidad o momento concreto del journey.

Composición recomendada: dos o tres pantallas completas con escalas compatibles. Evitar repetir pantallas sin explicar la evolución o la decisión.

### Web + mobile

Usar cuando haya que demostrar:

- Coherencia de una experiencia entre dispositivos.
- Adaptación de navegación o arquitectura.
- Relación entre un sistema visual y distintos breakpoints.

La comparación debe mostrar el mismo momento o una relación funcional clara, no dos capturas independientes.

### Design System

Usar para:

- Foundations, tokens, componentes y estados.
- Convivencia de formatos de información.
- Relación entre librería, producto y entrega.
- Evidencias de accesibilidad y QA.

No presentar una librería como inventario visual: explicar qué inconsistencia, riesgo o esfuerzo redujo.

### Web

Usar dos frames cuando ayuden a mostrar:

- Hero y contenido secundario.
- Relación entre página principal y módulos.
- Consistencia estructural entre layouts.

### Research y benchmark

Usar tablas o matrices cuando permitan comparar varias soluciones con el mismo conjunto de criterios.

- Categorías a la izquierda.
- Productos, competidores o alternativas en columnas.
- Presencia y ausencia mediante iconos solo si la leyenda es inequívoca.
- Acompañar la matriz con la decisión que produjo; no usarla como decoración de proceso.

### Vídeo

Usar cuando el movimiento o la secuencia sean parte del valor:

- Interacción real.
- Estados y transiciones.
- Coherencia desktop/mobile.
- Comportamientos que una captura no puede demostrar.

El vídeo debe tener alternativa estática y una explicación breve de qué debe observar el lector.

## 5. Patrones de copy reutilizables

Estos patrones se derivan de las slides; no son textos para copiar literalmente.

### Titular

```text
[Verbo de cambio] + [producto o servicio] + [resultado, tensión o contexto]
```

Ejemplos de estructura:

- `Evolucionar una app financiera sin romper la continuidad del servicio.`
- `Convertir una auditoría de accesibilidad en un sistema de entrega verificable.`
- `Unificar journeys de financiación para reducir fricción entre canales.`

### Introducción

```text
[Producto] necesitaba [cambio] porque [problema o contexto].
El reto era [objetivo] sin comprometer [restricción relevante].
```

### Responsabilidad

```text
Definí [decisión o sistema], coordiné [áreas] y acompañé [entrega o validación].
```

### Resultado

```text
El trabajo dejó [entregable o capacidad], permitió [cambio operativo] y creó una base para [siguiente evolución].
```

Si existe una cifra:

```text
[Métrica y periodo], según [fuente]. Se presenta como [impacto atribuible / contexto del producto / alcance].
```

## 7. Qué aplicar a los casos del portfolio

### En InOne

- Reforzar accesibilidad como sistema de trabajo: auditoría → priorización → documentación → entrega → QA.
- Mostrar ejemplos de criterios, no capturas del informe original.
- Vincular Design System, accesibilidad y despliegue progresivo.
- Mantener las valoraciones de las stores como contexto público, no como impacto causal.
- No publicar el `100% acreditado` hasta validar alcance y permiso.

### En accesibilidad financiera

- Usar la combinación `reto regulatorio + método reutilizable + coordinación técnica`.
- Diferenciar barreras detectadas, corregidas, verificadas y acreditadas.
- La cifra `28` solo puede usarse para MoneyToPay si se autoriza; no extrapolarla a otros productos.

### En canales y productos financieros

- Usar FinOnline y Fast Track como referencia de framing: continuidad, fiabilidad, conversión y coherencia omnicanal.
- No publicar reglas de scoring, contingencia, seguridad o arquitectura.

### En Facilitea

- Separar impacto del negocio de contribución del equipo.
- Fechar siempre las métricas de 2023.
- Priorizar decisiones concretas de journeys, Design System y delivery sobre una lista extensa de iniciativas.

## 8. Checklist para agentes

Antes de redactar o modificar un caso:

- Consultar primero `portfolio-estandares-y-buenas-practicas.md`.
- Identificar si la voz describe a Victor o al equipo.
- Clasificar cada cifra como impacto, contexto de producto o alcance.
- Añadir periodo, fuente y estado a cada número.
- No copiar una cifra de una slide a una página pública si sigue `pendiente-aprobacion`.
- No reutilizar pantallas originales cuando puedan contener producto, reglas o datos confidenciales.
- Elegir el formato visual porque demuestra una decisión: mobile, web, sistema, matriz o vídeo.
- Si no hay impacto defendible, usar un resultado cualitativo concreto o no incluirlo.
- Mantener claridad, impacto y credibilidad por encima de densidad o espectacularidad.
